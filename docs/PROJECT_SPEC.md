# Bookixo Pro: Project Spec (source of truth)

Mobile app (Flutter, Android + iOS) for salons that don't want to use the Bookixo web app.
Minimal by design. Anything not listed here is out of scope for v1.

## Brand
- App name: **Bookixo Pro**
- Colors: blue `#1A73E8` (primary), dark blue `#1560C4`, orange `#F59309` (accent). Logo: the Bookixo "b" with check.
- Clean, minimal, large tap targets. Light and dark mode.
- Match the `index.html` palette: light background/card/text/muted/border are `#F4F6FB` / `#FFFFFF` / `#14213D` / `#6B778C` / `#E4E8F0`; dark equivalents are `#0F1624` / `#1A2335` / `#EEF2FA` / `#98A4BB` / `#2A3550`. Success is `#12A150`.
- Login uses the CSS 170-degree gradient `#4A8DF0` (0%), `#1A73E8` (45%), `#1560C4` (100%), with aspect-ratio-aware endpoints. Its card and form controls remain light/white in dark mode.

## Roles (role comes from the server at login, never from local storage)
- **Owner**: can serve customers and never scans attendance. For the post-login menu increment, landing is derived from permitted mobile tiles, not role alone.
- **Employee**: never sees prices. Attendance is deferred in this increment; landing follows the same menu-driven rule.

### Implemented post-login menu increment
- After valid login/session restoration and shop-context gating, load `GET {baseUrl}/api/navigation/me?shopId=<selectedShopId>` with access-token Bearer authentication. The confirmed response is a top-level array of menu trees with nested `children` arrays.
- Flatten the tree into exact `menuKey` membership. For `shop-setup` only, also retain its immediate child-key relation. One mobile registry defines titles, icons, routes, kinds and order; web labels/routes/icons/roles/IDs do not control mobile UI.
- Operations is enabled by `bookings-pending` or `bookings-in-progress`; each key independently enables its queue tab. Dashboard uses `shopdashboard`; Offers uses `shop-offers-2`; Credits & Packages uses `shop-credits-packages`; Membership uses `shop-memberships`; Services uses `shop-services-list`; Shop Users uses `users-shop`; Shop Settings uses `shop-setup`. Unknown keys are ignored.
- Only Operations -> Queue directly; otherwise nonempty tiles -> Home; zero tiles -> No access. Add customers is excluded from this increment.
- Cache menu keys per account and selected shop. Freshness/refresh interval is 60 seconds, not a hard expiry: refresh at login, on throttled resume, and with Home pull-to-refresh; on recoverable failure retain same-account/same-shop cache even when older, with visible stale/error feedback. Without cache show Retry, never all tiles.
- **Approved Home redesign (implemented):** follow the hybrid Home layout in `DESIGN.md`, replacing the previous `index.html` all-horizontal visual reference. Keep the rounded branded header and one full-width teal Operations card (`#17A590` to `#0B7D6E`, CSS 135-degree gradient); show the seven secondary registry features as compact icon-led, distinct dark full-card gradients with white titles/icons in a responsive two-column grid with a single-column fallback. Dashboard retains orange branding in its icon area. On Home, the selected salon name with a chevron opens the existing chooser only for owners/shop admins with multiple accessible salons; other screens retain their current switch controls. Credits & Packages and Membership retain visible/semantic **Web only** badges and benefits pages saying **Currently available on Bookixo web** with the unconfigured CTA unavailable. Offers retains subtitle **Schedules & availability**, no Web only/Read only badge. Preserve registry order, exact menu keys, guards, combined Credits & Packages, tap logging, landing rules and exclusion of Add customers. No Home queue counts or catalogue/directory API calls are added.
- Home shop artwork uses confirmed authenticated `GET api/shops/{shopId}/logo` through the existing protected ACCESS-token client. `200` has JSON `{"logoUrl":"https://images.example.test/synthetic"}` (synthetic documentation fixture only); `204` with no body is confirmed absence. A malformed response or forbidden response remains a typed failure, not absence. Protected 401 recovery/logout is unchanged.
- The header displays the remote HTTPS shop logo in the existing 42px rounded crop, falling back to the bundled Bookixo logo during API/image loading, absence or failure. Flutter's separate image transport receives no login auth headers; JPEG/PNG decoding does not depend on path extensions. Failures log only fixed sanitized contexts, expose typed error state and offer friendly nonblocking Retry without disrupting menu access.
- Presigned logo URLs are memory-only and never logged or saved to durable storage. Scope is stable account identity, explicit login ownership and validated selected shop; token rotation alone does not reload artwork. New scope, Home manual refresh and each foreground entry refetch (single-flight). When valid `X-Amz-Date`/`X-Amz-Expires` metadata is present it schedules expiry refresh; no fixed 900-second lifetime or menu 60-second threshold is reused. An expired/403 image gets at most one logo-API retry per explicit refresh chain; decoding errors do not loop. Logout/scope replacement rejects late results and evicts only that logo's image-cache key.
- Guard routes, deep links and back-stack entries using current registry-derived tile membership. Queue tabs require their individual keys. The menu is a UI hint only; the server authorizes every API call.
- Secure menu payload schema v2 adds `shopSetupChildren` in the existing secure storage slot. Valid schema-v1 snapshots retain their flat permissions but grant no settings-child access; the next successful fetch/write upgrades them. Missing/malformed v2 edges are typed contract failures. Child-edge revocation prunes routes/back stacks even when flat key membership is unchanged. Same-scope stale/failure behavior and the 60-second refresh threshold are unchanged.
- Clear cached menu and in-memory/user-scoped state on logout, including in-flight response protection. Queue reads, customer lookup, walk-in creation, Pending-start and booking workspace use the confirmed authenticated booking APIs outside explicit demo mode. Indian phone numbers are sent as 10 digits; the backend adds +91. Employee UI does not show prices/totals/payment information. Attendance remains deferred.
- Queue realtime refresh is an optional unauthenticated Socket.IO connection configured only by `SOCKET_BASE_URL`; it is never inferred from `API_BASE_URL`. It uses Engine.IO 4 / Socket.IO, websocket transport, and `/socket.io`, with no token, cookie, or auth payload added by the mobile client. For a validated selected shop, subscribe with `subscribe` and `{targetType: "SHOP", targetId: "<shopId>"}`; accept the subscription only after the `subscribed` acknowledgement confirms `SHOP:<shopId>`, `SHOP`, and the matching target ID. Re-subscribe on every connection and refresh the protected REST queue after acknowledgement.
- Only `NEW_BOOKING`, `BOOKING_STARTED`, `BOOKING_CANCELLED`, and `BOOKING_COMPLETED` notifications with `targetType=SHOP` and the current shop ID trigger queue reads. Refresh only currently permitted Pending and/or In progress tabs through the existing access-token REST repositories. Debounce notification bursts by 400 ms, serialize reads, and perform one trailing read when another event arrives during a read. Never render/log notification payloads, change booking/customer/payment drafts, or retry mutations.
- Do not connect in demo mode, without a validated account/shop and queue permission, or without explicit socket configuration. Keep the 15-second queue polling fallback only before subscription acknowledgement and while disconnected/unavailable; retain pull-to-refresh. On foreground resume, reconnect/resubscribe and refresh authoritative REST data. Unsubscribe/disconnect on background, logout, account/shop/access change, and queue-scope disposal. Show nonblocking connection/recovery feedback; REST remains authoritative and keeps its existing employee price restrictions.
- **Accepted gateway security limitation:** the confirmed gateway has no handshake authentication or room-membership authorization. This mobile client deliberately sends no access/refresh tokens to it. CORS is not authorization. Anyone able to reach that gateway may be able to subscribe to shop notifications; this is a known deployment risk, not a security guarantee supplied by the app. Do not claim authenticated or authorized realtime delivery.
- Implemented with deterministic contract, cache/lifecycle, route/back-stack/dialog, queue and responsive widget coverage. See [Post-login home plan](./post-login-home/plan.md) and [implementation evidence](./post-login-home/batch-report.yaml). Backend/native-device verification remains outstanding; no test credentials were supplied.

### Services, Shop Users and Shop Settings
- All three are native registry destinations for either supported display role, controlled only by their exact server menu keys; no additional owner/employee permission gate. Landing remains Operations-only -> Queue, otherwise nonempty -> Home, empty -> No access. Home supports eight tiles with the existing responsive grid, dark full-card secondary gradients, white text/icons and reduced-motion-aware glyph animation.
- **Services** (`shop-services-list`, `/services`) is read-only and price-free. Reuse `BookingRepository.loadServices()` and its confirmed `GET api/public/shops/shop/services/{validatedSelectedShopId}` mapping (`id`, `name`, optional `parentId`, `isBookable`, `usual`). Parent categories precede their indented child rows; bookable parents remain visible. Missing parents and cyclic chains safely become ungrouped roots without dropping/duplicating records. No add/edit/delete controls. Explicit loading, empty and friendly error + Retry states.
- **Shop Users** (`users-shop`, `/shop-users`) reads `GET api/users/shop-users` through protected ACCESS-token Dio with encoded `shopIds=<validatedSelectedShopId>`, `page=0`, `size=20`, `sort=id,desc`. Consume Spring `content`, `number`, `size`, `totalElements`, `totalPages`, `last`; Load more follows metadata, not page length. Failures are typed; pagination failures retain existing rows and Retry the failed page. Reads are single-flight and scoped to account/login ownership, validated selected shop, scope revision and current permission; discard late responses on replacement, including rapid A -> B -> A.
- Directory records may contain `shopUserId`, `shopId`, `shopName`, `role`, `assignedAt`, `userId`, `email`, nullable `name`, nullable `phoneNumber`, nullable `active`. The minimal in-memory model retains only row/shop identity and displayed name/email/phone/role/active. Absent/blank name falls back to email; missing phone and unknown active status are explicit. No management actions. Never persist contacts, retain identity-provider subobjects/metadata, or log response/contact values. Tests/demo use synthetic `example.test` contacts only.
- **Shop Settings** (`shop-setup`, `/shop-settings`) shows only recognized immediate children of that parent in the current menu tree: `workday` -> **Workday**, `shop-gst-settings` -> **GST settings**, `shop-booking-qr` -> **Booking QR**, `shop-payment-config` -> **Payment settings**, `shop-logo` -> **Shop logo**. Unknown children, grandchildren and unrelated flat keys grant no child destination. Each `/shop-settings/<exact-child-key>` route requires both parent permission and its immediate edge, including direct links and restored/back-stack entries. Each opens **Available on Bookixo web** information only, with no inferred URL, browser launch, configuration endpoint or configuration action.
- Live Services/Shop Users use the confirmed APIs. Only explicit demo mode uses mock repositories; Settings remains intentionally informational.

### Native Offers (read-only compact tickets)
- Permission remains exact `shop-offers-2` for both supported display roles. The existing `/web/offers` route/deep links now render the native screen, preserving centralized registry-driven guards.
- Native Offers is read-only. Creating, editing and activation of offers or schedule rules remain on Bookixo web; no switches, raw-rule management rows, status PUT capability, master toggle or Undo. Menu permission grants access for either supported display role; there is no extra locally invented role gate. Unauthorized list/details/deep links use existing centralized redirects, never an upsell.
- List-only status is aggregated from **raw related rules**, including invalid/unknown schedules, after a complete successful rules load: any `rule.isActive=true` means **Active**; at least one rule and all false means **Inactive**; no related rules means **No rules**. Pending, failed or capped rules mean **Status unavailable**, never guessed from the parent offer or loaded subset.
- All counts loaded **offer records**. Active/Inactive count offer cards by the above aggregate, not individual rules; multiple active rules on one offer count once. No rules/unavailable cards are All-only. Header says **`<n> offers with active rules`**, including zero when every rule is false. Until rules complete, header is unavailable and activity chip counts are `—`, not definitive zero. Initial order is aggregated Active-first then alphabetical within groups; unknown status uses alphabetical order.
- Export retains schedule-revision checks across capture/permission awaits, so a rules refresh invalidates stale captures. Reads and export remain scoped to account/login ownership/validated shop/current permission.
- Start `GET api/shop-offers`, `GET api/offer-targets`, and `GET api/offer-schedule-rules` concurrently, **each** with `shopId=<validatedSelectedShopId>&page=0&size=100`, using protected ACCESS-token Dio. Parse Spring `content`, `number`, `size`, `totalElements`, `totalPages`, `last`. Drain each resource independently while `last=false`, maximum ten pages (0–9). A short or empty page is not completion. Publish the first offers page immediately and progressively append, independently of pending targets/rules. Show incomplete cap status, retain loaded records on resource failure, and provide resource-specific Retry; never replace failure with successful empty data.
- Offer fields: `id`, `title`, `discountType` (`FLAT`, `PERCENT`, tolerant unknown), numeric decimal `discountValue`, `startDate`/`endDate` (strict `YYYY-MM-DD`), `isActive`. Ignore response description/priority/stackable/shop metadata. Promotional value is **not a service price**; introduce no employee/service price fields. Render percent `n% / OFF`, flat `n / FLAT OFF`, drop trailing fractional zeros, infer no currency or free-item type. Unknown type is neutral and cannot export.
- Details/export only: **phone-local timezone** determines today. Recompute on local midnight and foreground resume without network polling; inject the clock for deterministic tests. Parent eligibility precedence is **Off** when disabled; otherwise **Expired** when end < today; **Upcoming** when start > today; **Active** on inclusive valid bounds. Missing, invalid or reversed validity is explicitly unavailable, never inferred, and cannot export. Date nullability remains unconfirmed. These parent/date helpers must not drive list badges, filters or counts. A disabled/expired parent can have an Active list badge but cannot export.
- Target fields: `id`, `offerId`, `targetType` (`SERVICE`/`SHOP`, tolerant unknown), `serviceMatchMode` (`ALL`/`ANY`/null), `isCombo`, `targetIds[]`, `targetNames[]`, `hasAnotherOfferForSameService`. Ignore singular targetId/targetName. Join by offer ID, never title. Each SHOP record yields a voucher even without names; each SERVICE record with usable names yields one. Skip empty-service and unknown-type records. Distinct records remain separate even with identical names. Keep Combo/ALL/ANY wording; missing/unknown mode uses neutral "On <names>" without guessed and/or. Successful complete load with no eligible targets shows **No targets set up yet. Set this up on Bookixo web.**
- Rule fields: `id`, `offerId`, `scheduleType` (`ALWAYS`, `WEEKLY`, `MONTHLY`, `DATE`, tolerant unknown), `dayOfWeek`, `dayOfMonth`, `specificDate`, `startTime`, `endTime`, `isActive`. Retain isActive, but do **not** filter on it. Preserve source fields while deduplicating identity/semantic schedules; merge weekly same normalized time window into sorted unique Sunday-first days (1 Sunday…7 Saturday). Different windows stay separate. A window ending exactly one second before start modulo midnight (including 00:00:00–23:59:59) is all day. Other forward modular durations <60 seconds are invalid; 60 is valid. Equal start/end semantics are unresolved: explicitly ignore as invalid, not 24h. Unknown/invalid schedules are ignored with fixed sanitized diagnostics and visible feedback, disabling export conservatively. Known malformed resource structures are typed failures. ALWAYS all-day or all seven weekdays displays **Every day**, never "Always"; partial all-day weekly schedules use day circles and short labels; restricted windows/monthly/date are text. Append validity; no usable rules gives validity only with diagnostic feedback when applicable.
- Scope reads and export by stable account identity, explicit login ownership, validated selected shop and exact current permission; reject late results after logout/shop/account/permission changes. Preserve server authorization and existing money safety.
- List and voucher layout follows DESIGN and the supplied compact colored-ticket screenshot. Exactly one tappable card per offer: full-height left value panel FLAT blue `n / FLAT OFF`, PERCENT orange `n% / OFF`, white large value and tiny label, trailing zeros trimmed, unknown neutral. Right content has title/badge, merged schedule day circles/text underneath, and validity at bottom. No raw rule IDs, switches or repeated individual schedule sections; no list eligibility heading. Rule inactivity never grays discount colors. Same-window weekly summaries merge (Sunday=1), while different windows and diagnostics remain visible. Show "No schedule rules" only after complete successful rules read; pending, failed and capped reads stay explicit. Whole card opens existing details. Notice: **Create or edit offers and schedules on Bookixo web.** **Open web — unavailable** remains disabled because no approved URL exists. Home/order/subtitle and guarded `/web/offers/:offerId` remain unchanged.
- Details has one voucher per eligible target, cycling Gift/Ocean/Sunset/Classic, shop name from validated context, two-line target ellipsis, schedule/validity, decorative stripes (not an actual redemption code), Share and Save image below. Owner-only overlap warning remains outside the captured card. Off/Expired/Upcoming cards are dimmed and cannot export. Export is also disabled for invalid validity/unknown discount, any pending/failed/capped resource, or unusable diagnosed schedules. No false claim of share eligibility.
- Capture customer-facing card only as PNG at 3x. Share uses the native system sheet (including iPad origin), Save image uses the gallery; request permission **only on Save**, single-flight per target, typed friendly failures and eligibility checks after awaits. `share_plus` 13.3.1 / `gal` 2.3.3 APIs checked against installed lock and maintained package docs. Android legacy write permission is bounded through SDK 29; iOS photo usage strings added. Actual Android/iOS share/gallery behavior and live backend still require device verification.
- Production uses only the three confirmed GET APIs. Explicit demo mode uses read-only fixtures. Live authenticated backend and native-device verification remain outstanding.

### Login contract and display role
- Sign in with `POST {baseUrl}/api/auth/signin`, sending only `{identifier: trimmedInput, password}`. Email login remains supported. Staff phones accept 10 Indian digits starting 6–9, `91` plus those digits, or explicit international `+` with a nonzero country code and 8–15 digits. Spaces, parentheses and hyphens are presentation separators; `+91` must match Indian mobile format. Existing password is required; backend staff phone approval/synchronization controls eligibility.
- The canonical response email remains `AuthIdentity.email` and the refresh identity, never the entered phone. Challenge responses retain existing next-step guidance; no phone verification or new-password completion UI is added.
- Sign-in and refresh responses use a numeric integer `userId` (for example `5`); the data layer normalizes it to the internal string ID. Existing secure-session string IDs remain readable.
- Derive the display role from the server-issued Cognito `idToken` payload, not a stored role flag. Local JWT decoding does not verify signatures and is never authorization.
- Centralize group mapping: `OWNER`, `shop_admin`, `shop_owner` -> Owner; `shop_employee` -> Employee. Owner wins when both recognized roles appear. Unknown groups -> unsupported-role screen, never Owner or Employee by default.
- Password-change or challenge responses show a friendly next-step message for now; completing these flows is not in this login increment.
- Store tokens only in secure storage. Restore sessions and refresh before expiry using `POST {baseUrl}/api/auth/refresh` with `email` and `refreshToken` in the JSON body. Refresh returns the sign-in response shape; retain the existing refresh token if omitted, and replace it when returned.
- Protected APIs use the access token as Bearer, never the refresh token. Fetch shop context using `GET {baseUrl}/api/users/my-shop-context`; its response contains `shops` (id/name), `primaryShopId` and `primaryShopName`.
- An empty shop list blocks shop features and shows "No shop assigned" with Retry and Logout. Owners/shop admins can locally select an accessible salon from `shops`; there is no switch endpoint. All existing APIs use the validated selected `shopId`. Restore the account-scoped last-used preference from secure storage, otherwise use backend primary; one salon is automatic. Preferences may survive logout but never grant membership. Employees remain on assigned primary and cannot switch.
- Home, Queue, booking forms/details, No access and menu recovery expose the shared **Switch salon** chooser only to owners with multiple salons. Confirm discarding unsaved form/services/payment work; cancel preserves input. Claim/create/save/discard/payment requests block switching until settled and are never automatically replayed. A successful switch removes dialogs/back stack and clears branch-specific customers/drafts/features/repository caches; monotonic scope revisions reject late results including A→B→A. Preference failures are nonblocking with Retry; tokens and login ownership remain separate from account identity.
- Local development uses `http://localhost:8080/` with debug-only HTTP support; Android emulator uses `http://10.0.2.2:8080/`, and physical devices require a supplied LAN IP. Release builds require HTTPS.
- Logout clears tokens, shop context and user-scoped provider state. See [Login flow plan](./login-flow/plan.md) for implementation order and remaining questions.
- Login, persistent production owner salon switching, post-login navigation, the native read-only Dashboard, and authenticated queue/walk-in/booking-workspace APIs have Flutter implementations and deterministic tests. Booking details, services, employee draft saves, owner pricing/payment configuration, completion and discard are live outside explicit demo mode. Run instructions are in the root [README](../README.md). Home is menu-driven for both supported display roles; attendance remains deferred. No live authentication/device sign-off is implied.
- Attendance QR scan is DEFERRED in the post-login menu phase. Users with only Operations go straight to Queue; other permitted tile combinations follow the menu landing rule.
- shop_owner and shop_admin are the same role in the app (owner view). Employee group name:shop_employee.
## Booking statuses (must match the Bookixo web app)
- **Pending**: customer is in the queue.
- **In progress**: an employee/owner has claimed the customer. Services and discount are added here.
- **Completed**: owner records payment (same final step as web "Complete Booking").
- "Ready to pay" is NOT a status. It is a flag on an In progress booking once services are saved.

## Business rules
- **Claiming**: tapping a Pending customer claims them for the current user (status becomes In progress). Server accepts only the first claim; the second gets a conflict error and the app shows "Already with <name>". Others see "With <name>".
- **Add services**: shows the user's most-used services as badges, plus a search box over the full service menu. Multi-select. Optional notes.
- **No prices for employees**: employee screens never display prices, totals or payment details. A shared API response may include service prices; employee presentation must omit them.
- **Discount**: optional, percentage or fixed amount. Server validates it against limits.
- **Editing after save**: the user who served can edit services, discount and notes until the owner completes the booking.
- **Owner serving**: owner can claim Pending customers and edit their own work. Owner cannot take over a customer another staff member is serving.
- **Complete payment (owner)**: shows customer, who served, services with prices, subtotal, collapsible "Applied pricing rules", discount applied, final amount, payment mode (Cash, Card, UPI, Bookixo; required), "Mark as paid". GST, membership and credits are calculated by the backend and folded into the final amount; not shown separately in v1. Owner sees "Edit services" only on bookings they served.
- **Add customer**: first name (required), last name, phone (required), gender (optional), birthdate, anniversary.
- **Walk-in**: phone number first. If it matches an existing customer, show the customer and hide all other fields, then "Add to queue". If not, show the full customer form. Normalise phone numbers (country code, spaces) before matching.
- **Locked web tiles** (Membership, Credits, Packages): tapping opens an upsell page with a benefits list and "Get started on web". Log a tap event for each tile and the button, to measure demand. Offers retains tap logging but opens native read-only compact offer tickets and voucher details as approved above.
- **Attendance**: employee scans the shop QR. Later: record location at scan time and flag (not block) if far from the shop.

## Out of scope for v1
Payment processing, split payments, editing the final amount, invoices/printing, offers create/edit/activation (web-only), membership/credits/packages management, geolocation attendance, push notifications.

## Tech decisions
- Flutter (stable), Dart null-safe, **Riverpod** for state, **go_router** with role-based redirect guards, **dio** for HTTP, secure token storage (`flutter_secure_storage`), a maintained QR scanner package (verify on pub.dev before adding).
- Feature-first folders: `lib/features/{auth,attendance,queue,services,payments,customers,dashboard,offers,upsell}` each with `data/`, `domain/`, `presentation/`. Shared code in `lib/core/`.
- All network calls live in repositories under `data/`; widgets never call dio directly.
- Queue refresh: pull-to-refresh, optional shop-scoped Socket.IO invalidations, and a 15-second polling fallback while realtime is not subscribed. Prevent double submits.
